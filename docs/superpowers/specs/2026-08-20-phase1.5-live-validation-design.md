# AI Research Observatory Phase 1.5 真实数据验收设计

## 1. 背景与问题

Phase 1 已能从 GitHub Releases、RSS / Atom 和配置化 HTML 来源采集 Evidence，并生成带 Coverage 的中文日报。但当前 `--date` 只决定运行产物的归档日期，并不限制远端内容的发布时间：GitHub 返回最近若干 Release，Feed 返回其中最近若干条目。

当前 Evidence 去重又仅发生在单个日期目录内。因此，相同来源内容在不同运行日期再次出现时会被重复写入，并可能每天重复进入日报。这与“每天只关注新发现动态”的使用目标不一致。

## 2. 目标

Phase 1.5 建立清晰的时间语义并完成真实来源验收：

1. 相同 `evidence_id` 在整个本地观测站中只保存一次。
2. 日报展示“自上次成功扫描后首次发现的 Evidence”，而不是强制限定“当天发布”。
3. 保留来源原始 `published_at`，使延迟进入 Feed 的文章仍可被发现。
4. 同一天或跨日期重复扫描相同快照均不产生重复日报项。
5. 无需真实等待三天；用确定性测试模拟三天，再运行一次真实 `core` 扫描验证外部来源。

## 3. 非目标

- 不引入 Signal、Claim、Direction、评分或 LLM 总结。
- 不引入 SQLite；SQLite 研究图仍属于 Phase 2。
- 不增加 Windows 计划任务、GitHub Actions 或 X 集成。
- 不把“来源不可用”解释成“没有动态”。
- 不按 `published_at == run_date` 做严格过滤，因为这会漏掉延迟发布、时区差异或晚到的 Feed 条目。

## 4. 方案选择

### 4.1 未采用：按发布时间过滤当天内容

实现简单，但会漏掉延迟进入 Feed 的内容，也会让时区和缺失发布时间影响日报完整性。

### 4.2 未采用：每天保存完整来源快照

便于审计来源当天返回了什么，但相同 Evidence 会跨日期重复，占用注意力，并模糊“新动态”语义。

### 4.3 采用：带首次发现元数据的全局 Evidence 日志

Evidence 以内容寻址 ID 在全局不可变日志中只保存一次。每个日志记录同时保存首次发现的 `run_date` 与 Evidence 正文；日报按日志记录的 `run_date` 读取，不创建第二份每日索引。

该方案保持 Phase 1 的 JSONL、local-first 和可审计特性，同时避免提前引入 Phase 2 数据库。

## 5. 时间语义

- `published_at`：来源声明的原始发布时间；缺失时沿用现有推断与诊断规则。
- `collected_at`：该 Evidence 首次被观测站发现的时间，等价于 Phase 1.5 的 `first_seen_at`。
- `run_date`：用户选择的运行分组日期，保存在全局发现记录中并用于 Coverage、运行清单和日报筛选；不改变远端查询窗口。
- `run_id`：首次发现并保存该 Evidence 的运行 ID。后续重复扫描不会改写它。

## 6. 存储布局

```text
evidence/
  ledger.jsonl                         # 全局不可变发现记录，evidence_id 唯一
runs/
  YYYY-MM-DD/<run_id>.json             # 每次运行的 Coverage 与来源诊断
reports/
  daily/YYYY-MM-DD.md                  # 当日首次发现 Evidence 报告
```

全局日志的每行采用以下结构：

```json
{
  "schema_version": 1,
  "run_date": "2026-08-20",
  "evidence": {
    "evidence_id": "...",
    "collected_at": "2026-08-20T01:00:00+00:00",
    "run_id": "20260820T010000Z-abcd1234"
  }
}
```

`run_date` 是首次发现的分组日期，`evidence.collected_at` 是首次发现的精确时间。整条记录通过一次 JSONL 追加写入，不需要跨文件事务。

## 7. 组件与接口变化

### 7.1 EvidenceLedger

保持调用方接口稳定：

- `append(run_date, evidence) -> bool`
  - 全局不存在 `evidence_id`：追加一条包含 `run_date` 与 Evidence 的发现记录，返回 `True`。
  - 全局已存在：不写任何重复记录，返回 `False`。
- `read_date(run_date) -> tuple[Evidence, ...]`
  - 从全局日志读取首次发现 `run_date` 等于指定日期的 Evidence。
- 新增 `read_all() -> tuple[Evidence, ...]`，用于完整审计和后续迁移。

内部新增不可变 `EvidenceRecord(schema_version, run_date, evidence)` 负责 JSON 转换。`Evidence` 的内容寻址算法和公开结构保持不变。

Phase 1 仍是单进程运行，因此本阶段不引入文件锁；未来加入并发调度前必须重新设计原子写入。

### 7.2 Runner

Runner 无需改变公开签名。`appended_count` 的语义从“当日文件新增数”明确为“本次运行首次发现的全局新 Evidence 数”。来源成功但全部重复时仍为 `healthy`，`collected_count > 0`、`appended_count == 0`。

### 7.3 Daily Report

日报继续使用 `EvidenceLedger.read_date(run_date)`，因此自然只展示当天首次发现的 Evidence。标题下增加时间语义说明：

> 本报告展示本次观测周期首次发现的 Evidence；发布时间可能早于运行日期。

Coverage 继续展示来源状态、获取数和新增数。

### 7.4 CLI

命令保持兼容：

```powershell
ai-observatory scan --root . --date YYYY-MM-DD --profile core
ai-observatory render-daily --root . --date YYYY-MM-DD --run-id RUN_ID
```

帮助文本与 README 明确说明 `--date` 是运行分组日期，不是远端发布时间过滤条件。

## 8. 数据流

```text
远端最新 N 条
  -> Adapter 生成含 published_at 的 Evidence
  -> EvidenceLedger 按 evidence_id 查询全局日志
     -> 新 Evidence：单次追加 {run_date, evidence} 到 ledger.jsonl
     -> 已存在：不重复写入
  -> Run manifest 记录 collected_count / appended_count
  -> Daily report 按 run_date 读取当日首次发现记录
```

## 9. 错误处理与恢复

- 全局日志损坏或存在无法解析的 JSONL：明确失败，不静默跳过，避免生成错误去重结论。
- 单条 JSONL 记录必须先完整序列化，再执行一次追加写入；解析到截断或损坏行时明确失败，不静默生成日报。
- 真实来源超时、限流或解析失败继续隔离为 `unavailable`，不阻断其他来源。
- 所有运行产物继续被 `.gitignore` 排除，Token 和请求头不得写入任何日志。

## 10. 测试与无需等待三天的验收

### 10.1 确定性模拟

使用同一份 RSS 快照模拟三次运行：

1. `2026-08-20` 首次运行：全局新增 1 条，当日日报 1 条。
2. `2026-08-20` 重复运行：全局新增 0 条，当日日报仍只有 1 条。
3. `2026-08-21` 再次运行相同快照：全局新增 0 条，次日日报 0 条。

再使用加入第二条内容的新快照模拟 `2026-08-22`：只新增并展示第二条 Evidence。

### 10.2 损坏检测测试

构造截断或非法 JSONL 行，`read_all()`、`read_date()` 和后续 `append()` 必须明确失败，不能把损坏日志误判为空日志或继续追加。

### 10.3 真实 core 冒烟测试

在确定性测试通过后运行一次真实 `core` 扫描：

1. 检查 8 个核心 GitHub 项目和启用的官方 Feed。
2. 生成 Coverage，逐项记录 `healthy / unavailable / stale`。
3. 生成中文日报并检查是否不超过 10 条。
4. 同日立即重跑，确认 `appended_count == 0` 且日报不重复。

真实扫描用于发现 URL、限流和解析问题；即使部分来源不可用，也不修改离线测试的确定性结论。

## 11. 验收标准

1. 全量离线测试通过。
2. `ledger.jsonl` 中不存在重复 `evidence_id`。
3. 相同快照跨日期运行不会在新日期日报中重复出现。
4. 新快照只产生真正新增的 Evidence。
5. `published_at`、首次 `collected_at` 和 `run_date` 三种时间含义可区分。
6. 真实 `core` 扫描能生成完整 Coverage；不可用来源不被描述为“没有动态”。
7. 同日真实重跑不新增重复 Evidence。
8. 运行产物和认证信息不进入 Git。

## 12. 后续边界

Phase 1.5 通过后再设计 Phase 2。届时 SQLite 接管 Signal、Claim、Direction 和关系查询；本阶段的全局 Evidence JSONL 继续作为不可变原始证据账本，而 SQLite 只建立可重建索引和研究图。
